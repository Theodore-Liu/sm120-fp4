# SM120 kernel census: the ledger

One row per shipped kernel path read against the exact oracle (`sm120fp4/oracle.py`) on the RTX 5090 (sm_120, driver 610.47). The four-week
test of the direction (opened 2026-10-10): fewer than three distinct confirmed defects by 2026-11-07 downgrades it. "Conformant" means every
output element inside the oracle's bound (exact product plus the fp32-accumulation slack at the tensor core's truncation unit of one ulp per addition, 2^-23, since 2026-10-11, plus output rounding), on the shapes and operands the
report names, and is read with the detectability floor the oracle module documents (a one-code fault at K = 4096 is below fp32 noise).

## Tally toward the four-week test

Distinct defect classes found and reproduced: **1** (the cuDNN grouped block-scaled GEMM's mid-tile segments, wrong output with no error,
NVFP4 and MXFP8, on two devices; root cause in FlashInfer's wrapper, a local fix verified, see `docs/flashinfer-grouped-fp4-rtx5090.md`). Environment findings, not kernel defects: 1 (`bmm_fp8`'s cutlass backend taking the WSL2 virtual
machine down on the 5090 while running clean on a bare-metal PRO 6000). Confirmed by maintainers: 0 (every issue draft awaits the
author's review before posting). Precision designs documented, not defects under the API's contract: 4 (FlashInfer `cutlass_fused_moe` NVFP4's FC1, activation and per-route FC2 written as bf16; the b12x W4A4 micro and
dynamic backends' bf16 atomic scatter; the W4A4 static backend's FC2 in bf16 partials per 256; the W4A16 path's bf16-packed routing
weight). Conventions documented, not defects: 3 (E4M3 / E2M1 tie rounding; the b12x fused MoE's w13 half order; b12x W4A4's `w1_alpha`
as the input-quant scale). Crashes on an unsupported part already guarded in the next release: 1 (FlashInfer 0.6.16 `mm_fp8`).
Reports that did not reproduce: 1 (TensorRT-LLM issue 14154 on this part).

## An instrument note

The first W4A16 run read every backend non-conformant with identical statistics on both backends. Two independent backends agreeing with each
other against the oracle is the signature of a wrong operand on the caller's side, not of two kernels wrong the same way; the cause was the
scale layout (`prepare_bf16_fp4_weights` takes the 128x4-swizzled scales, as its docstring says; the probe had passed them row-major). Fixed, every
backend is conformant. The rule for the census: a verdict of non-conformant is written down only after the operand contract has been read
from the library's own documentation and a second backend or library disagrees with the first.

A second note (2026-10-11, `docs/fp8-gemm-rtx5090.md`): a fault that vanishes exactly at m = 1 is a layout fault in a per-row operand,
not a kernel fault, since at one row every layout of an (m, g) tensor is the same bytes. vLLM's blockwise FP8 path takes its
activation scale column-major, which its docstring does not say and its own caller does; read the caller before the verdict.

A third note (2026-10-11, `docs/flashinfer-b12x-w4a4-moe-rtx5090.md`): when a kernel's rounding points are not in its docstring, fit them
with structured probes (identity weights that make the output read out an intermediate; top-1 with weight 1 to isolate one GEMM)
before any verdict; the first W4A4 model differed from the kernel on half the elements by one ulp, which is the signature of a
wrong rounding point, not of a kernel fault. The same fitting corrected two parts of every oracle here: the accumulation unit
(tensor cores truncate, one ulp per addition) and the binade of the output rounding (taken at the top of the interval).
